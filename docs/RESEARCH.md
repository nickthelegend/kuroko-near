# Kuroko protocol research — 2026-11-09

## Relay and settlement

- Official [Market Makers overview](https://docs.near-intents.org/integration/market-makers/introduction.md): a market maker listens to quote requests, returns a signed quote, and the selected intent is settled by the Verifier contract, `intents.near`.
- Official [WebSocket reference](https://docs.near-intents.org/integration/market-makers/message-bus/websocket.md): `wss://solver-relay-v2.chaindefuser.com/ws`. Authenticate the handshake with `Authorization: Bearer <PARTNER_JWT>`. Subscribe by JSON-RPC `subscribe` with `params: ["quote", {"tokens_in": [...], "tokens_out": [...]}]`; subscribe separately to `quote_status`. Quote events carry `quote_id`, `defuse_asset_identifier_in`, `defuse_asset_identifier_out`, one of `exact_amount_in`/`exact_amount_out`, `min_deadline_ms`, and auction timing. Respond by `quote_response` with the same `quote_id`, one `quote_output` amount, and `signed_data`. `quote_status` reports quote/intent/transaction hashes. The docs show two event envelope shapes; a consumer must validate actual frames rather than assume either sample is definitive.
- Official [relay RPC](https://docs.near-intents.org/integration/market-makers/message-bus/rpc.md): `POST https://solver-relay-v2.chaindefuser.com/rpc` uses `X-API-Key: <JWT>`. It is an authenticated quote and publish API, not a public way to watch solver traffic.
- Official [solver quickstart](https://docs.near-intents.org/integration/market-makers/quickstart.md): Partner Portal approval and KYC/KYB are required for a Partner JWT. Mainnet inventory must be deposited in `intents.near`; register a signer public key through `add_public_key`.
- At 2026-11-09 14:35 UTC an unauthenticated WebSocket upgrade returned **HTTP 401, `authentication required`**. No quote stream or dated relay fixture can truthfully be produced without the JWT.
- Official [signing format](https://docs.near-intents.org/integration/verifier-contract/signing-intents.md): a NEP-413 response signs the hash of a Borsh-serialized payload with 32-byte base64 nonce, recipient `intents.near`, and a JSON message containing `signer_id`, deadline, and a `token_diff` intent. The key and signature are `ed25519:` plus base58 bytes. The sample solver's [hashing implementation](https://github.com/defuse-protocol/near-intents-amm-solver/blob/main/src/utils/hashing.ts) includes the NEP-413 domain prefix `2^31 + 413`.
- The [Verifier's account abstraction](https://docs.near-intents.org/integration/verifier-contract/account-abstraction.md) says **every public key registered to an account can sign intents on its behalf**, including key-management intents. A NEAR function-call access key restricts on-chain transactions, but does **not** restrict signatures supplied off-chain to the Verifier. Consequently, the proposed “function-call key that can only sign quotes within the constitution” is not enforceable by simply issuing a function-call key. A safe production design needs a contract-owned signer in an attested TEE with verifiable policy enforcement, or a verifier-level restricted-key feature. An off-chain `if` statement is not a custody boundary.

## Reference implementations

- The official [AMM solver](https://github.com/defuse-protocol/near-intents-amm-solver) refreshes `mt_batch_balance_of` reserves, prices exact-input/output requests with constant-product math, signs a `token_diff` intent, caches its hash, and matches `quote_status` to its own quotes. Its checked-out `main` README calls `RELAY_AUTH_KEY` “currently unused” and its WebSocket code opens without a header; the current docs require a Partner JWT. Kuroko must follow the **current docs** for authentication. The sample's private signer can act on all `intents.near` balances; it is not a restricted vault key.
- [Rhea's lending solver](https://github.com/rhea-finance/lending-near-intents-solver-golang) shows a `NO_LIQUIDITY` response, auction win via `swap_hash`, funding inventory, and final signed quote. It sends the bearer token on WebSocket connect. This is a useful asynchronous inventory pattern but does not provide a vault custody boundary.
- [1Click docs](https://docs.near-intents.org/integration/distribution-channels/1click-api/quickstart/introduction.md) confirm no Intents testnet. Rebalancing requests must start with `dry: true`; any real swap requires a funded mainnet account and explicit human approval. The [hackathon rules](https://nearhackathon.com/HACKATHON.md) put all mainnet signing behind explicit human confirmation.

## Design consequence

Until the Partner JWT exists, Kuroko can display a relay setup state and query public on-chain data, but cannot label public 1Click quotes or historical explorer trades as live relay quote requests. Until a verifiable restricted signer exists, deposited user assets must not be handed to an unrestricted off-chain solver key. The vault contract and local-chain tests can still prove share accounting and the controls enforced *inside the vault*; they cannot prove the Verifier checks Kuroko's constitution during an independently signed settlement.
